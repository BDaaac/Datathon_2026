## Правила игры
- **Продукт**: работающий сервис (UI + API) по публичному URL, а не сабмит-файл. Оценка автоматическая через API на 5+ тестовых видео; финальное снято под другим углом.
- **Метрика**: 7 критериев, 100 баллов (см. REQUIREMENTS.md). 55 баллов — детекция, локализация, классификация; 15 — нормативка; 30 — устойчивость, продукт, архитектура.
- **Цена ошибок**: пропуск нарушения недопустим, ложных срабатываний как можно меньше. Порог выбираем с приоритетом recall на уровне видео.
- **Лимит**: < 5 минут на видео (10–145 с, ≥29 fps, ~29 МБ, .mov).
- **Ограничения**: всё локально; без облачных AI API; модели только open source с коммерческой лицензией; без лиц; без звука; акты только РК.
- **Ресурсы**: GPU организатор не даёт. На хакатон 24 часа, дедлайн 12:00. Питч только для шортлиста: 5 + 2 минуты.
- **Решение команды**: обучаем на Kaggle, готовые веса запускаем локально в сервисе. Сначала модель; бэкенд и фронт команда делает сама.
- **Жюри**: ForteBank (кассовая дисциплина, безопасность, внутренний контроль). Им нужен инструмент-подсказка проверяющему, а не юридическое заключение.

## Данные (по FAQ)

- Разметка: на видео метка «нарушение» и таймкод (например, 11-я секунда). **Типа нарушения нет** — таксономию строим сами.

## Класс задачи (гипотеза)
Составная задача:
1. **Временная детекция событий (event spotting) в видео** при слабой разметке: вердикт на видео + таймкод, мало данных (~40 роликов). Подзадачи: видео-уровень (есть нарушение?) и момент (когда?).
2. **Классификация типа события** без разметки типов: своя таксономия → ручная разметка типов на train (40 видео — посильно) + zero-shot для новых типов.
3. **Сопоставление с правилами**: справочник `rules.yaml` (тип → наблюдаемый признак → документ, пункт), заполняется вручную по adilet.zan.kz / НБРК. Ссылки только из справочника, никакой генерации ссылок моделью.
4. **Продукт**: асинхронный сервис (очередь задач), UI, API по схеме.

### Бейзлайн (быстрый, сквозной)
Кадры с шагом 2–5 fps → детектор людей/рук/объектов + поза (модели с Apache/MIT-лицензией) → правила-эвристики по зонам кассы (покидание рабочего места, посторонний в кассовой зоне, деньги/сумка вне зоны…) → JSON по схеме. Цель — рабочий путь от загрузки до ответа API, даже если ловит мало типов.

### Кандидаты сильного рецепта
- **A. Эмбеддинги видео-модели + временной классификатор.** Скользящие окна 2–4 с → эмбеддинги предобученной видео- или изобразительной модели → классификатор «нарушение в окне», обученный на окнах вокруг размеченных таймкодов (позитивы) и остальных (негативы). Пик скора = таймкод, кадр в пике = доказательство.
- **B. Локальная мультимодальная модель (VLM) как классификатор типа и автор описания.** Кандидатные окна от A или бейзлайна → несколько кадров → локальная VLM с вопросами-чек-листом по каждому правилу из `rules.yaml` → тип + краткое описание видимого. Покрывает новые типы в тесте. Риск — скорость в 5 минут и лицензия модели.
- **C. Поза + объекты + треки как признаки** (более устойчивы к смене ракурса, чем пиксели) → GBDT/небольшая сеть по окнам.

### Проверка опровергающих наблюдений (EDA, см. findings.md)
1. **Сработало частично.** Нарушение определяется контекстом и состоянием объектов (сейф открыт, деньги/телефон/сумка/еда на столе, кто стоит со стороны кассира), а не самим действием: те же входы, подходы к сейфу и уходы есть в чистых роликах. → Упор на **зоны + объекты + люди во времени**, а не на «распознавание действия» по всему кадру.
2. **Частично.** Сцена одна, актёров двое, ракурсов 3–4 → высокий риск выучить сцену. Аугментации ракурса обязательны; дубликаты Х-4/Х-47 и Х-5/Х-48 — одна группа в CV.
3. **Не сработало.** Таймкод стоит на начале действия → позитивное окно = [t−1; t+3] с.

### Обновлённый подход (после EDA)
- **Основа (C, расширенный)**: детектор людей и объектов (телефон, сумка, чашка/еда, деньги/пачки, мешок, сейф и его дверца) + поза/руки → зоны сцены (рабочее место кассира, место клиента, сейф, дверь) → события во времени. Правила по типам дают тип, таймкод и кадр; обучаемый классификатор по окнам решает «нарушение / нет» для рецидивных случаев.
- **Зоны должны переживать смену ракурса**: задавать зоны относительно найденных объектов (стол, сейф, дверь), а не фиксированными пикселями.
- **Второй трек (A)** — эмбеддинги кадров/клипов + классификатор окна — включаем, если правила не покрывают «не определённые» ролики (1, 32, 33, 47).
- **VLM (B)** — только если на VPS будет GPU (на CPU не уложится в 5 минут); роль — описание кадра-доказательства и проверка спорных окон.

### Что опровергло бы гипотезу (исходная формулировка)
1. Нарушения различимы только по мелким объектам (купюры, пломбы, документы), а не по позам и перемещениям → упор на детекцию объектов/VLM, а не на позу.
2. Ролики — повторы нескольких постановочных сценариев с почти одинаковыми кадрами → риск переобучения на сцену; таймкод важнее типа; нужна аугментация ракурса и свои съёмки.
3. Таймкод размечен не на момент действия (начало/конец эпизода, «бездействие») → меняется определение позитивного окна и правило выбора таймкода.

## Валидация (план)
40 видео — мало: leave-one-video-out или GroupKFold по видео. Метрики: recall/precision вердикта по видео, |Δ таймкода| в секундах, доля верных типов (по нашей разметке), время обработки. Отдельная проверка устойчивости: аугментация ракурса (поворот, перспектива, кроп) на отложенных видео + свои съёмки под другим углом.

## Где выполняется код
- **Обучение и эксперименты**: Kaggle (GPU) через API — извлечение эмбеддингов, обучение классификатора, оценка VLM. Видео держим только в приватном датасете (данные — только в рамках хакатона).
- **Сервис** (предварительно): VPS с публичным URL. Kaggle-ядро не подходит как постоянный сервис.
  - CPU-VPS: детектор + поза на 2–4 fps для ролика до 145 с — ориентировочно 1–3 мин, укладывается в 5 мин. VLM — нет.
  - GPU-VPS: всё, включая небольшую VLM.
  - Веса скачиваем на VPS заранее; при обработке интернет не нужен (требование переносимости).
