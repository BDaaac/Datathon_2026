# Что требуется от ML для окончательной приёмки

Интерфейс `Analyzer()` / `Analyzer.run(path)` сохранён. Файлы `solution/`, `datathon/` и корневая `.venv` сервисом не изменялись.

**Блокер приёмки подтверждён:** `contract-report-final.json` содержит `passed: false`. Один Х‑14.mov обработан за 240,88 с, пять одновременно — все `failed` по бюджету 285 с. Сервер не зависает, JSON корректен и файлы удаляет, но без ускорения ML текущая машина не выполняет SLA жюри. Необходимый бюджет следует обеспечить внутри ML, без уменьшения полноты проверки на стороне сервиса.

1. **Прямые ссылки на нормы.** Сейчас `description` содержит текст нормативного источника, но в `solution/rules.json` нет URL. Добавьте проверенную ссылку `https://adilet.zan.kz/...` непосредственно в `description` каждого нарушения вместе с документом и пунктом. UI уже безопасно превращает эти ссылки в кликабельные. Сервис не придумывает правовые основания и не хардкодит таксономию.
2. **Производительность на длинных видео.** Первый Windows-прогон Х‑14.mov при пяти загруженных моделях и параллельной сборке Docker превысил 285 с; свободной памяти было менее 1 ГБ. Этот прогон не доказывает предел модели на свободной машине. Последующие Docker-прогоны с 1/2/3 torch-потоками также не уложили пять одновременных роликов в лимит. В сервисе дополнительно ограничены FFmpeg-потоки (по умолчанию их было 16 на видео). Итоговые замеры — `VALIDATION.md` и `contract-report-final.json`. Если итоговый прогон не проходит <300 с, нужен бюджет времени/ускорение внутри `Analyzer.run`; сервис не меняет FPS, правила, модель или пороги. Проверять пять копий Х‑14.mov одновременно, включая очередь и загрузку, командой из README.
3. **Обновление набора весов.** Build-скрипт читает литерал `DET_REPO` из `solution/pipeline.py`, скачивает одну фиксированную ревизию D-FINE и проверяет `Analyzer()` офлайн. При добавлении новых моделей нужны список репозиториев, ревизии, лицензии и способ подготовки. Тогда обновить только `service/prepare_weights.py` и зависимости/аргументы Docker.

Сервис ограничивает OpenCV и FFmpeg одним потоком и повторно устанавливает число torch-потоков после `Analyzer()`, поскольку текущий конструктор Detector переопределяет этот параметр. Битый MOV проверяется до вызова `run`, чтобы пустое видео не превратилось в `no_violation`.
