Скриншот: `ui-validation.jpg`.

## Производительность

Используется оригинальный Х‑14.mov: 28 718 927 байт, около 143 с. Пять ML-процессов, по два torch-потока, OpenCV один поток. Docker Desktop: 18 логических CPU, лимит памяти около 7,44 GiB.

Первый запуск на Windows при одновременно работающей сборке Docker и свободной RAM менее 1 ГБ превысил 285 с. Сервис вернул `failed` по таймауту и удалил файл. Этот прогон не прошёл критерий скорости.

На Intel Core Ultra 5 125H (14 ядер / 18 потоков) в отдельном Docker-прогоне с двумя torch-потоками одиночный файл успешно завершился примерно за 184 с. Пять параллельных файлов превысили 285 с: все пять получили `failed`, в `/data/uploads` осталось 0 видео. Лог: `contract-docker-threads2.log`.

С одним torch-потоком одиночный файл завершился за 231,67 с (POST 0,36 с). Все пять параллельных задач также превысили лимит; отчёт `contract-report-threads1.json` имеет `passed: false`.

С тремя потоками одиночный файл завершился за 225,42 с (POST 0,45 с). Одновременно с ним проверялся более короткий UI-ролик; этот одиночный замер не является изолированным сравнением CPU-настроек. UI завершился до начала пяти параллельных загрузок. Пять длинных видео снова превысили лимит: `contract-report-threads3.json`, `passed: false`.

Выявлена дополнительная конкуренция за CPU: OpenCV использовал **16 FFmpeg-потоков на видео**, хотя `cv2.setNumThreads(1)` был выставлен. Параметр `OPENCV_FFMPEG_THREADS=1` добавлен в локальный адаптер и Docker; `CAP_PROP_N_THREADS` в финальном контейнере подтвердил значение **1**. Эта настройка описана в [справочнике OpenCV](https://docs.opencv.org/4.9.0/d6/dea/tutorial_env_reference.html). Модель, FPS и правила не менялись. Контрольный прогон: `contract-report-final.json` (2 torch-потока + 1 поток декодирования на каждый из пяти процессов).

**Итог финального прогона: `passed: false`.** Все проверки 401 и неверных файлов прошли. Одиночный Х‑14.mov: POST **3,27 с**, полный ответ `done` **240,88 с**, JSON Schema и JPEG прошли проверку. Все пять параллельных задач завершились `failed` по внутреннему лимиту 285 с; клиент получил терминальные ответы за **287,33–288,30 с** с учётом загрузки, опроса и очистки. Это корректная обработка таймаута, но **не выполнение требования жюри «пять done <300 с»**. Увеличивать дедлайн для маскировки проблемы не стали.

Ускорение ML или другое вычислительное окружение — оставшийся блокер автоматической приёмки. Прогоны доказывают результат на этой машине и этой версии модели; перенос на другой CPU требует повторного `contract_test.py`. Тестовые видео не передавались во внешние сервисы.

## Ограничения сдачи

- В ML-описаниях пока нет прямых URL нормативных актов. UI умеет показывать переданные Adilet-ссылки; требование к ML записано в `NEEDS_FROM_ML.md`.
- Публичный URL, VPS, HTTPS и публикация не настраивались — по заданию это отдельный этап.
- При выключенном сервере очистка оставшегося после аварии файла возможна только при следующем запуске. В работающем сервисе неудачное удаление сохраняется как обязанность очистки и повторяется.
- Проверки сервиса не оценивают юридическую корректность или точность ML. Типы, нормы и модель не изменялись.
